# Showpass Mobile Automation Proposal

We want a test that buys a ticket in the Showpass app and confirms the ticket was issued. We’ll try the same guest checkout in Beta on iOS and Android with Appium + WebdriverIO, Detox, and Maestro.

## Goals

1. Start in **Explore** and buy a ticket as a guest. Check the confirmation in the app, then look up the order to confirm the total, ticket type, and issued ticket. [App checkout handoff](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/mobile/src/screens/BuyerScreens/PurchaseScreen/PurchaseScreen.tsx#L125-L148) · [Ticket readiness](https://bitbucket.org/showpass/web-app/src/5184fb7ed70ed5ccab2e0467345ea9127c331eb5/apps/financials/api/venue_based/viewsets/invoices.py#lines-616:632)
2. Run checkout in CI on iOS and Android. Have the job install and launch the Beta app. Save the logs and a screenshot if the test fails.
3. See how much work it takes to add and update tests, and how the suite holds up as it grows to hundreds of cases. Start with the same second scenario for each tool, such as signing in during checkout, returning from bank verification, or seeing the confirmation change with the Venue setting. Keep discounts, assigned seating, and custom questions in Playwright. [Checkout browser suite](https://github.com/showpass/showpass-playwright/tree/2e5addb9be4881af4d951bca5323568cfdfee381/tests/core/checkout) · [Seating browser suite](https://github.com/showpass/showpass-playwright/tree/2e5addb9be4881af4d951bca5323568cfdfee381/tests/core/assigned-seating) · [Native sign-in](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/mobile/src/util/webview/helpers/index.tsx#L100-L109) · [Stripe payment flow](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/core/src/shared/modules/payments/gateways/StripePaymentGateway/StripePaymentGateway.ts#L1810-L1815) · [Confirmation setting](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/core/src/app-contexts/public/features/checkout/hooks/useStandalonePostPurchaseNavigation.ts#L72-L86)
4. See which hardware checks we can automate. To run them unattended, we’d need a device that stays connected and a way to present a barcode or card and check the result.

## How the tools stack up

Before the pilot, we’ll set the same targets for all three tools. Agree on suite size, run time, first-attempt pass rate, how much time we can spend setting up and updating tests, and what we can spend to run the suite.

- **Checkout coverage.** Two tickets mean the tool can use the WebView through the visible UI. Three mean it can work with the WebView directly and has a documented way to reach secured fields or frames from another domain on one platform. Four mean there’s a documented path to work inside those frames on both platforms. For five, buy the ticket on both platforms, see the confirmation, and verify the saved order and issued ticket. Any method that proves the full checkout can earn five.
- **CI readiness.** All three get three tickets for documented ways to run tests and save failure details. For five, show that the CI job installs the Beta app and runs checkout on iOS and Android, reports the result, and keeps logs and screenshots when a check fails. ## Pilot plan

1. **Get the builds ready.** Start each tool from the same Showpass revision, device targets, Beta Venue settings, and test payment setup. Write down any build changes a tool needs. On iOS, `ios_sim_beta` builds the simulator app. On Android, start with the direct Beta APK for buyer checkout. Confirm which buyer build the team wants to cover because the checked-in production release set uses the Stripe organizer build. [iOS simulator lane](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/mobile/fastlane/Fastfile#L579-L592) · [Android build profiles](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/mobile/release/distribution-profiles.json#L1-L59) · [Organizer navigator](https://github.com/showpass/showpass-frontend/blob/f1ca342cd7d5b109446631515c2248c17251dcc6/packages/mobile/src/navigation/AppNavigator/StripeAppNavigator.tsx#L4-L6)
2. **Run checkout in CI.** Agree on the number of runs and when to retry. Give each attempt a fresh buyer email and basket. If jobs run in parallel, give them separate ticket inventory. Keep the first failure in the results. If we can’t tell whether the payment went through, look up the order before trying again.
3. **Pick a tool once we have results.** It needs to complete the purchase and verify the order and ticket in CI on both platforms. Agree up front on which hardware checks are required. Compare setup time, what it takes to keep adding and updating tests, how run time and flaky failures change as the suite grows, and what it costs to run. Before using the suite for releases, decide who looks after the app builds, test failures, and devices.
