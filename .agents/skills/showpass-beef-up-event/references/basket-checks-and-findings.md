# Basket checks and bugs during Showpass setup

These checks belong to creating/updating the scenario. Apply the Vault's current canonical evidence, financial, Inventory, finding-classification and browser-report rules. They are a bounded smoke check and opportunistic bug reporting, not a whole-app audit or authorization to transact.

## Prove that the created items reach the basket

The receiving checkout tester uses this section in an independently approved job. The Builder uses the findings guidance for setup.

1. **Record the starting basket and cleanup path before adding.** Confirm the relevant environment, Organization, Customer/session, item identity and sale state. Determine the supported remove/release action. Protect existing Customer lines, discounts and answers. Use an existing authorized empty/isolated session when available; do not clear the user's basket, sign them out or launch another browser to make testing easier. If safe cleanup/isolation cannot be established, continue independent setup and name the exact basket blocker.
2. **Select useful distinct items/quantities.** Check each newly created or materially changed sellable Level, ticket type or Product variant on its supported sales path, with a valid quantity. Include selected Membership Levels, standard admission, changed timed/VIP experiences, group minimum, relevant Product variants and the intended mixed basket where applicable. Use the offering's actual supported sales path; a Membership Level does not require an Event ticket picker. Benefits and discount/credit definitions are not standalone basket items: test their eligible parent/item path within the authorized entitlement scope, or mark the missing Member/code check Blocked/Not run. Reuse successful additions for the mixed check instead of rebuilding the same basket. A Package is purchased through its parent; do not require a package-only child to be directly sellable. Seller-only tickets belong to an authorized Box Office path, not ordinary public checkout. Do not create orders to inspect those paths.
3. **Follow the actual add/Checkout control into the basket/review stage.** Prove the Membership Group/Level, Event/date, ticket or Product variant as applicable, quantity and expected item grouping from actual basket lines. Check Member-information prompts only as far as the authorized non-submitting flow permits; previewing those fields is not proof of saved Member details. Check selected custom experience times when displayed, base prices and visible applied rules against saved setup. For a mixed credited/paid scenario, confirm separate intended lines, eligibility and the excluded paid item. Apply a credit/code only when that action is authorized, the actual controlled code exists and its reservation/use behavior is understood. Do not invent a code or treat a code input field as proof of successful redemption.
4. **Get fresh basket proof.** Reopen/refresh the supported basket view and verify the expected items/quantities remain once, with no duplicates or substituted variant/date. A ticket picker, incremented quantity, enabled Checkout button, accepted request or loading view alone is insufficient. Stop before final purchase, payment authorization, legal acceptance, order submission or any action that issues free/comp tickets. A $0 checkout is still an order with side effects.
5. **Check unavailable paths honestly.** A deliberately future-on-sale, sold-out, hidden or password-protected tier may correctly reject an ordinary add. Verify its expected restriction without changing dates, exposing private stock, bypassing controls or consuming the last unit to force a pass. Use the eligible path only when supported and authorized. Call the positive add check Not run/Blocked when the required sale state or access is absent; a negative-path pass does not prove successful addability.
6. **Restore the basket and verify release.** Remove only this run's additions and temporary code selections through supported controls; preserve the original basket. Verify its original lines/quantities and any affected reservation/credit/Inventory state through the available supported proof. If full release is delayed or unavailable, record the real pending state and follow the documented timeout/recovery within scope. Do not silently leave scarce stock held or reset counters in Admin. Preserve data and report a concrete blocker if safe cleanup fails.

Record **items checked / exact basket result / cleanup result / not-run variations** in the existing note, with screenshots at the actual action and fresh result. Keep addability, price/fee calculation, credit redemption, completed payment, Member issuance, benefit use, renewal, ticket generation, ticket issuance and actual admission as separate claims. A successful Level basket add does not create a Member, grant usable benefits or prove a renewal. Do not trigger Member/ticket batches or consume an existing Member's benefits merely to demonstrate configuration. If a case requires completed orders or historical purchases, a successful basket smoke does not meet that prerequisite.

## Flag bugs without derailing setup

Watch for failures in the work already being done: valid creation/save rejected, fields silently lost, wrong timing or item relationships, incorrect Group/Level benefit scope or validity, bad eligibility, incorrect public visibility, failed basket adds, duplicates, mismatched prices/quantities or unreleased reservations.

- Establish the intended result from the case/requirement, actual saved configuration and current source. Separate confirmed product failure from a guessed cause. Expected validation, an unavailable module, missing permission/test data, a pending request and a browser-control error are not automatically bugs.
- Capture the minimum safe setup, exact visible actions, Expected/Actual, affected typed IDs, environment/date and screenshots/request evidence already available. Avoid personal data, full credit codes and barcodes. Check final saved/basket state before retrying anything with money, access or Inventory side effects.
- Reproduce safely when needed to establish the failure; do not repeat financial actions, create duplicate records or broaden into unrelated screens just to improve a report. A corrected click/input can resolve a tool problem. An unexplained observation stays Inconclusive with its missing proof.
- For each confirmed bug, use the available **showpass-bug-drafter** skill and add one local `BUG-*` draft beside the affected walkthrough in the canonical note. Use `fix (area) | observed problem` plus GIVEN/WHEN/THEN, with actual and intended outcomes distinct. Check existing drafts/issues when readily available; link several affected checks to the same issue instead of duplicating it. A local draft does not authorize Jira creation, messages or source fixes.
- Tell the user promptly when a confirmed bug changes what can be prepared or makes a required basket check fail. Preserve evidence before a supported workaround. Continue independent safe configuration; do not claim a required broken path is ready because another path worked. Apply canonical stop/financial gates where relevant.

The final results table must retain every failed, blocked, inconclusive or unrun selected check, link each bug draft and state whether the basket was restored. Summarize no confirmed bugs when that is the actual result; do not manufacture a finding to satisfy the workflow.
