# Showpass Branch Digest

Apply the [shared engineering review layer](<../../../06 Prompts/Showpass Release Engineering Handoff.md#apply-the-review-layer>) if the work becomes a live assignment or release handoff. Scoped drafting and read-only findings can finish at the requested scope. Reuse existing reviews when supplying evidence for the same revision.

Turn the exact backend and frontend branch diffs into a report that Product, QA and Support can understand on the first read. Title the report **Release <user-provided version> — Upcoming changes**. Use the release supplied by the user, not a version inferred from package files, branch names or tags; confirm the release label from the request or its existing report. Keep the supplied version in the document title, H1, frontmatter, filenames and evidence. Reuse it for revisions of that report; obtain the version when starting another release whose label the user has not supplied. A release label is not proof of deployment. Organize the report around individual meaningful changes within recognizable workflow groups. Each change answers: what changed; where it came from (Jira, PR and verified commit links); what to test and why this change motivates that test; and whether saved Qase cases cover it. Use compact expandable entries so the default view stays scannable. Do not make the reader infer the connection from a separate area-wide regression list. Feature acceptance belongs to the teams owning the changes; regression is shared by the whole QA team. There is no page limit, but the reader should not need to work through every detailed change or commit.

## Defaults and boundaries

- Backend: the sibling `web-app` checkout.
- Frontend: the sibling `showpass-frontend` checkout.
- Vault: the repository that contains this skill.
- Compare each repository's current branch with its own verified remote `master` or `main`. This means `develop` when it is checked out; do not silently substitute another branch. Honor explicit branch/base overrides. The two repositories can have different targets.
- When refreshing an earlier report, retain its agreed comparison targets unless the user changes them. A checkout later moving to master/main does not silently turn a requested develop comparison into an empty report. Freshly fetched explicit remote targets can be read without switching the checkout; label those targets and the separate checkout pull result.
- The user has authorized Git fetch and safe Git pull for this workflow. Refresh each new comparison without asking again. For an editorial revision, reuse and label the existing snapshot unless the user requests updated source. This does not authorize source edits, branch switching, stashing, resets, merging, rebasing, pushing or publication to another service.
- Read applicable `AGENTS.md` instructions and the vault's `01 Repositories/Backend - web-app.md` and `01 Repositories/Frontend - showpass-frontend.md`. Backend source establishes business behavior; frontend source establishes how people reach and use it.
- Use the bundled report references and assets for wording and visual style.

## 1. Refresh and fix the comparison

Use the bundled collector. It fetches each remote and pulls only a clean, attached current branch with an existing upstream, using `git pull --ff-only`. It never switches branches or repairs divergence. Baselines must resolve to remote `master`/`main`, or an explicit base requested by the user.

```bash
python3 <skill-dir>/scripts/collect_branches.py --output /private/tmp/<unique-run>/branch-evidence.json
```

Options: `--backend-target`, `--frontend-target`, `--backend-base`, `--frontend-base`, `--backend`, `--frontend`, `--remote`. See `--help`. Use `--offline` only for explicitly requested cached analysis or isolated tests. Use filesystem/CLI tools rather than desktop apps or browsers.

Inspect both results even if one fails. Dirty files, detached HEAD, a missing upstream, divergence, missing base, shallow history and failed fetch/pull remain visible. Mark an affected repository **Not fully refreshed** at the top, explain why and label any cached comparison. Continue the unaffected repository. Do not describe cached results as current. If both `main` and `master` exist and the remote default does not choose one, ask which base to use while continuing independent work.

Record collection time in `America/Edmonton`, repository, branch/ref, base SHA, target SHA, merge-base SHA, ahead/behind counts, refresh results and whether local edits were excluded. A branch with no upstream is local-only even if its base fetch succeeded.

Use `BASE...TARGET` to review changes introduced since the common ancestor. Use `BASE..TARGET` for target-only commits. Count base-only commits separately; never describe them as additions. If target equals base, report no branch-only changes without inventing a release range. Multiple best common ancestors require an explicit ambiguity warning.

Check apparent changes against the current base as well: target-only history can include cherry-picked, reverted or independently merged work whose final behavior is already shared with the base. Use direct base-to-target file comparisons and Git patch-equivalence checks. A common file differing for another feature does not mean the original feature is still different. Keep those commits in the evidence ledger and identify shared/history-only work separately; do not present it as an upcoming change.

## 2. Read changes and explain behavior

Before drafting, read the relevant sections of the backend's `UBIQUITOUS_LANGUAGE.md`, then the frontend's `ARCHITECTURE.md` and affected module README/AGENTS guidance. Resolve overloaded words to the actual actor, record and lifecycle in the pinned source; the glossary guides naming but does not prove behavior. Apply the vault QA Handbook's UI terminology: Organization in Dashboard, Venue for its backend/Admin record, and distinct Customer, Attendee, Member and Venue Employee roles.

Use the product's visible words in the digest and manual instructions, with a short everyday explanation where needed. Keep precise model/service names in supporting evidence. In particular, distinguish basket selection, financial transaction and issued ticket; ticket transfer and Membership transfer; voucher uses and stored money credit; Member lookup and completed benefit Scan In; guestlist Reservation, checkout allocation and explicit Hold; and Refund, Void and Exchange. Name the actual action in change summaries: write voucher Refunds when restoration belongs to Refund, and state the different Void result where readers could confuse them. Do not use “returns” or “Void/return” to imply shared credit behavior. Keep an actual Return control’s visible name, explaining its refund routing where relevant. Do not rename saved Jira/PR/Qase titles to fit editorial wording. Record material terminology corrections and their sources in the evidence sidecar.

The collector is an inventory, not the summary. Read actual patches and relevant surrounding source at the recorded SHAs, starting with the backend. Use pinned revisions (`git show <sha>:<path>` and `git diff <merge-base> <target-sha> -- <paths>`) so dirty files or moving branches cannot change the evidence. Batch related reads; account for all changed files, including deletions, binaries, migrations and dependency/CI changes. Filenames and commit subjects alone do not establish behavior.

For every distinct change establish:

- **What changed:** what a Customer, Attendee, Member, Organizer or Venue Employee can do, or the specific old problem addressed. Claim an old failure only when old code supports it.
- **Who and where:** actual screen, workflow or operational process and supported affected clients. Trace shared backend changes to callers, including unchanged clients when relevant.
- **Why it matters:** concrete customer/business impact. Avoid “improved stability” and other vague benefits.
- **Setup and limits:** relevant permissions, settings, flags, companion-repository dependencies and migrations. A flag name in code does not establish its live value or broad availability.
- **Evidence:** repository, source files/commits, Jira, PRs and uncertainty.

Group the reader-facing report by recognizable workflows or areas, such as checkout and returns, Inventory and admission, Dashboard and approvals, public pages, integrations, reporting, and internal work. These are reading groups, not claims that unrelated changes are one feature or launch. Use short change titles and expand the supporting detail on demand within each group. Several commits/PRs can form one meaningful change; do not create a card per commit or display every entry in full by default. Keep exact tracking, setup and source records in supporting evidence. Net-reverted and already-shared work stays in supporting evidence.

## 3. Resolve Jira and PR links

Read [references/tracking-links.md](references/tracking-links.md). Discover connected tools for the actual Git provider and use Atlassian Rovo for Jira. Resolve PRs through commit associations as well as explicit merge/squash subjects. Branch names and commit text are leads, not proof a PR landed.

Within each change entry, provide **Where it came from** with clickable **Jira**, **PRs** and **Commits**, followed by the change’s Qase assessment. Derive commit URLs from the verified repository remote and saved change-to-commit evidence, not keyword similarity. Keep long commit lists expandable; do not imply every commit touching the same file implements this change. Keep the exact links mapped to each underlying change in supporting evidence. Provide clickable record links when found, otherwise a truthful missing/blocked label. Keep source-derived links visibly marked when the record could not be read. Never invent PR numbers, Jira titles or status. Missing connector access limits enrichment; it does not stop the source-backed report.

## 4. Link saved Qase cases and suggest titles

Read the vault's `05 Tooling/qasectl.md` and follow its read path. By default, add verified Qase IDs beside the grouped changes and shared regression checks. For a presentation revision, keep the source snapshot and record Qase's separate retrieval time. Use one complete project snapshot with local filtering; reuse `05 Tooling/scripts/collect-release-coverage.mjs` when appropriate. Do not infer absence from an incomplete read or a single keyword.

Inspect final candidates' full saved setup, parameters, actions, expected results and postconditions. Link the real case ID to its actual case URL. Distinguish matching assertions from **Partial** cases and cases whose expectations **Need review**; briefly name the missing check. Related titles alone do not establish coverage. Where no exact saved case is verified, say so and suggest **test titles only**, following the vault's naming rules. Prefer strengthening an existing case when the missing check fits its purpose; a title suggestion is not automatically a new-case recommendation. Do not invent IDs, draft full cases or write to Qase. Engineering/operator work can be marked as engineering validation without manufacturing manual cases.

Keep the digest readable: **Qase for this change** beside the change and **Qase for this test** beside each assigned check. Retain exact matches, mapping limits and title-only proposals locally. A journey-level partial match does not automatically cover each individual test: show only relevant saved starting cases, retain their limits, and label the exact match Unknown/Needs review when it has not been established. Do not silently promote a related title to verified coverage. Preserve project, read completeness/count, reviewed IDs, mapping reasons and proposed titles in the existing evidence sidecar. A definition match is not an executed result. If Qase access is blocked, label mappings Unknown and explain the read failure; keep proposals tentative rather than declaring cases missing.

## 5. Produce the report

Read [references/report-format.md](references/report-format.md). Produce:

1. A canonical Markdown report: short overview and workflow groups containing compact change entries, each with source links, Qase and causally related tests, followed by a brief evidence link. Full change/commit/file records belong in the existing evidence sidecar, not the main reading flow.
2. A matching responsive HTML report using [assets/report-shell.html](assets/report-shell.html), with working Jira/PR/Qase anchors. Keep teal/coral/ink colors, rounded cards, clear labels and natural page height. A PNG is optional only when requested; HTML preserves clickable links.

Default: `<vault>/02 Feature QA/Branch Digests/<Edmonton-date>-release-<user-provided-version>.md`, with matching `.html` and `.evidence.json` files. For example, `2026-11-13-release-36.39.0.html`; preserve every version component when appending extensions. Put actual comparison refs in the report/evidence, adding them to the filename only when several comparisons for the same release/date need distinction. Honor the user's destination. A requested new dated report preserves previous dated reports. Update the canonical report for the same request rather than leaving parallel drafts. Preserve existing user edits and apply the vault's Obsidian conventions when writing there.

Choose highlights for actual impact without a fixed card count. Prefer roughly five to eight groups when the scope warrants it, without filling a quota. Account for every meaningful change in a group and supporting evidence; completeness does not mean displaying every record in full. Write for someone who knows Showpass but does not read code. “Added … so …” and “Fixed an issue where …” work when evidence supports them. Label code **On this branch**, not “shipped,” “live,” “ready,” or “tested.” Tests are **Not run** unless results were collected for these exact revisions. Keep Qase mapping limited to the changed behaviors and regression shortlist; it does not certify complete coverage, execute tests or issue a release decision.

## 6. Tie each test to the change that motivates it

Read the vault’s canonical quality standard and relevant QA Handbook guidance when selecting regression. Build the shortlist from shared code changes and their callers, not a generic all-product checklist or a copy of each Jira acceptance criterion.

- Before writing each selected journey, resolve its essential prerequisites from the vault’s QA Handbook, `05 Tooling/Qase Test Case Writing Rules.md` (Short, Actionable Prerequisites and Explain Showpass Terms And Where To Find Them), then the pinned backend eligibility checks and frontend control visibility. Do not load unrelated skills merely because they exist. Put the exact setting label, owning Organization/Event/Ticket Type, location, required value, employee permission and ticket/order state beside the check. Explain inherited settings and how hidden controls become available. Distinguish saved settings from feature switches and permissions. Name the supported setup owner/Admin record when preparation needs that access; record original values and restoration. Source review does not prove the deployed setting is enabled.
- Keep prerequisite requirements separate from live readiness. Before any scenario-data mutation, confirm the environment/Organization and ask for the exact relevant flag/module/permission/payment values. Reuse user confirmations for the same scope; unknown values block dependent execution. Admin access, even read-only or through an API, requires separate explicit permission. A report naming an Admin-managed prerequisite does not authorize inspecting or changing it.
- Confirm that the prepared purchase can reach the named action. A free order, voucher-discounted paid order, package, voucher ticket use and stored money credit may have different eligibility. Do not substitute Refund, Return free tickets, Void or Exchange because a button is missing. If setup cannot be established, state the exact missing prerequisite and mark execution Blocked. Verify that the chosen path actually exercises the changed behavior; a related Customer return may process order lines differently from one staff Refund. Re-read the whole Prepare/Test/Expected/Stop here section after any setup correction, including repeated display instances, linked Qase limitations and supporting evidence.
- **Owning teams:** test the new/changed feature, its detailed rules, configuration and rollout acceptance. Do not assign that full matrix to central QA.
- **Whole QA team:** share a prioritized pack protecting existing purchases, money/fees, Inventory, admission, ownership, saved configuration, permissions and downstream results around the changes. Divide checks across testers and clients; do not require everyone to repeat the entire pack.
- Display one business-risk priority badge per regression item: **Critical**, **Major**, **Medium** or **Low**. Choose by the potential impact of the journey failing, following the vault standard; do not fill every level for appearance. Keep stable check IDs and execution status in evidence, and state the overall Not run status once in the report’s regression guidance. Do not put IDs, First/Then ordering or Not run in each badge.
- For each regression area, give **Prepare**, a small numbered **Test / Expected** checklist and **Stop here**. Aim for roughly three to five distinct checks when that fits the scope, not a quota. Name exact starting records, quantities, roles and controls; translate outcomes into visible evidence such as one refunded ticket, two restored voucher uses or one valid replacement. Explain necessary terms. Separate Refund, Void and Exchange onto independent orders. State policy-dependent money/fee expectations from the actual setup rather than inventing universal rules. Keep priorities and Qase links beside each area, with partial-match notes and title-only suggestions expandable. Keep source reasoning in evidence. A compact checklist can be longer than one paragraph without becoming the full feature matrix.
- Write regression actions as short numbered instructions and expected results as short bullets. State how many orders/tickets are needed, whether tickets belong to different Events, which action happens once, what is left untouched, and the expected before/after counts. Avoid compressed phrases such as “voucher-backed lines,” “separate journeys,” “control,” “grant,” or “reconcile records” when ordinary wording explains the task. Distinguish preparation from purchases performed in the test so the reader never buys twice by mistake. Keep exact flags and permission keys in concise setup notes. Preserve the evidence and policy-dependent money/fee checks; clearer wording must not remove them.
- Include a clean successful sale independently from failure/recovery. Keep Refund, Void and Exchange separate and preserve applicable financial, Inventory and access proof. Trace unchanged clients using changed shared behavior; mark physical-device checks explicitly. Supported controls differ by client.
- Label proposed checks **Not run**. Missing setup/access/downstream proof is Blocked, not a pass or automatic Not applicable. Reuse existing cases/automation without claiming their actual coverage unless it was inspected. Do not run browser tests, mutate data, write Qase or issue a release decision just because a regression summary was requested.

Under the specific change, show **What to test and why**. Explain the chain in everyday language: the changed behavior/shared code → the existing result it could affect → what this check proves. Link the change to its Jira/PR/commits above it. A broad group heading such as Checkout or Dashboard, or “shared code changed,” is not enough justification. Split a large regression area into its individual checks when its tests protect different changes. Distinguish a direct change check, related regression, and an optional preparation/comparison baseline; do not imply all baseline checks are required by the diff. Keep one full copy of each checklist under its primary motivating change. Other relevant changes show their own reason, Qase limits and a link to that same checklist, not duplicate instructions. Keep exact local prerequisites, numbered actions, expected results and stopping limits with each full check; tailor shared setup when splitting without losing coverage or telling the reader to execute unrelated journeys. Preserve stable IDs/results and dependencies in evidence, and make links open hidden parent entries in HTML. Keep ownership/shared execution guidance brief, with no separate responsibility banner or disconnected regression list. Keep inventories in supporting evidence.

## 7. Verify and deliver

- Reconcile all target-only commits and changed files with change groups, internal-only classifications, net-reverted explanations or explicit unresolved items. Several commits can map to one PR/change. Verify every detailed record has a reading group, without expanding the main report back into individual cards. Keep an unreviewed portion visible rather than declaring a complete report.
- Verify Qase IDs against the retrieved snapshot, explain partial/uncertain matches, and ensure suggested gaps contain titles only. Confirm every underlying change and regression check has a mapping or explicit engineering/unknown status.
- Check terminology against the backend glossary, affected source contracts and frontend UI wording; preserve record/lifecycle distinctions while keeping manual instructions readable.
- Mentally follow each check from its stated starting screen: are the actor, settings, permissions, order/ticket state and actual action available? Resolve essential setup through the vault guides and source before delivery; do not leave “where enabled,” “eligible order” or “prepared setup” unexplained when that condition controls whether the test can be run. Clearly label any remaining source/UI/access gap.
- Verify Jira/PR provider, repository, labels and URLs. Check HTML links and claims match Markdown; escape inserted text and attributes. Keep evidence beside its claim.
- Check for unresolved HTML slots, clipping, mobile/print readability and missing details. Use an authorized render/preview capability if available; otherwise state that visual rendering was not checked. Do not open a desktop browser.
- Verify the source checkouts have no unexpected edits. Remove the exact temporary run directory after necessary evidence is preserved. Keep final deliverables and evidence needed to repeat the comparison.
- Reply with links to both reports, the comparisons, refresh outcome and material limits. The report should be immediately readable without more formatting instructions. Check that each change answers what changed, where it came from, what to test and why, and whether Qase covers it. Verify every displayed test has a specific motivating change and visible selection reason, shared tests have one full copy, and feature acceptance remains with owning teams.
